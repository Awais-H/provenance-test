# acme-payments

Merchant payments, settlement, and webhook delivery.

This is a synthetic repository generated by `seed/build_seed.py` for the Provenance
demo. It is not a real service.

---

## Sentry

This repo reports errors to Sentry, and every merge to `main` becomes a Sentry
release named after its merge commit SHA. That naming is the whole mechanism:
Provenance asks GitHub for PR #N, reads back `merge_commit_sha`, and asks Sentry for
`firstRelease:<that sha>`. Both systems already agree on the string, so "which
incidents did this PR cause" is an exact join rather than a full-text search for the
characters `#N` in issue titles.

| Piece | Where |
|---|---|
| SDK init, capture helpers | [`observability.py`](observability.py) |
| Instrumented failure paths | `webhooks/delivery.py`, `search/indexer.py`, `payments/settlement.py` |
| Release + commit association | [`.github/workflows/sentry-release.yml`](.github/workflows/sentry-release.yml) |
| Traffic, so the release has issues | [`scripts/simulate_incidents.py`](scripts/simulate_incidents.py) |

With `SENTRY_DSN` unset every helper is a no-op, so nothing here needs credentials to
import, test or run.

### Setting it up

**1. Create the Sentry project.** A Python project in your Sentry org. Note the org
slug and project slug — they are in the URL: `sentry.io/organizations/<org>/projects/<project>/`.

**2. Install the Sentry GitHub integration.** Sentry → *Settings* → *Integrations* →
*GitHub* → *Add Installation*, and grant it this repository. This is what turns the
commits attached to a release into suspect commits and PR annotations. Without it the
release still exists and Provenance still resolves incidents; you just lose the
commit-level attribution inside the Sentry UI.

**3. Create an auth token.** Sentry → *Settings* → *Auth Tokens* → *Create New Token*,
with scopes `project:releases` and `org:read`. `project:releases` is what
`action-release` writes with.

**4. Add four repository secrets.** *Settings* → *Secrets and variables* → *Actions*:

| Secret | Value |
|---|---|
| `SENTRY_AUTH_TOKEN` | the token from step 3 |
| `SENTRY_ORG` | your org slug |
| `SENTRY_PROJECT` | your project slug |
| `SENTRY_DSN` | the project's DSN, from *Settings* → *Client Keys (DSN)* |

**5. Trigger it.** Merge anything, or run the workflow by hand from the *Actions* tab
(`workflow_dispatch`). A green run leaves one new release in Sentry with that PR's
commits attached, and one issue whose `firstRelease` is that release.

### Running it locally

```bash
pip install -r requirements.txt
SENTRY_DSN=<your dsn> SENTRY_RELEASE=$(git rev-parse HEAD) \
  python scripts/simulate_incidents.py
```

Omit `SENTRY_DSN` and the same paths run with nothing reported, which is the useful
way to check the script still works after changing the code it exercises. `.env` is
read too, if you copy `.env.example` to it.

**Do not point a local run at the real DSN before CI has run at least once.** An
issue's `firstRelease` is fixed the first time Sentry sees it and is never
recalculated, so a local run claims all three issues for whatever release your
working copy is on. CI then emits them again under the merge commit SHA, but
`firstRelease` still points at your laptop -- and Provenance reports the PR as having
caused no incidents, with no error to explain why. Recovery: delete the issues in
Sentry and re-run the workflow.

### A caveat worth stating

`scripts/simulate_incidents.py` and anything under `simulations/` induce the failures
they report. They are real events from real instrumentation with real stack traces,
but they are not observed production traffic — this library has no deployment. Issue *counts* here mean
nothing. The issue-to-release-to-PR *linkage* is the part that is real, and that is
the part Provenance consumes.
